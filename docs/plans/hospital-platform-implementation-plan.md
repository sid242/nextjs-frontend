# Dental and eye hospital platform implementation plan

**Goal** · Extend the existing SaaS foundation so a clinic can register a patient, book or check them in, record and sign an encounter, issue a bill, and reconcile payment in one workspace.

**Source** · `Plan_doc_hospital.md`, 12 October 2026, sections 1–16. This roadmap uses the PRD's product phases and adds an engineering Phase 0. The backend work breakdown is in `nodejs-backend/docs/plans/hospital-backend-implementation-plan.md`.

**Baseline** · Both PRs were open against `main` on 21 November 2026. The frontend baseline is `dccaac2` and the backend baseline is `da3a581`. [Frontend PR #1](https://github.com/sid242/nextjs-frontend/pull/1) · [Backend PR #1](https://github.com/sid242/nodejs-backend/pull/1)

Current code anchors include `src/proxy.ts`, `src/app/api/proxy/[...path]/route.ts`, `src/features/{auth,tenants,platform,privacy,files,realtime,billing}` and the workspace layout at `src/app/(app)/w/[tenantSlug]/layout.tsx`. Keep clinical UI in feature slices, place new paths in `src/config/routes.ts`, and put server data in TanStack Query with tenant and branch in keys wherever the response is branch-scoped. Express remains the authority for access decisions.

## Phase 0 · Confirm pilot scope and prove the foundation

- [ ] Confirm the pilot clinics, launch specialty mix, branch visibility policy, staff identity requirements, and whether ABDM is a contractual launch gate. Use India-first outpatient/day-care and an English, tablet-friendly staff web app as planning assumptions. Sequence dental before eye for the first end-to-end slice while sharing the same visit model. The full Phase 1 release includes both specialties unless product explicitly narrows MVP.
- [ ] Review the two PRs as the baseline. Run local sign-in, role restriction, dashboard and seat-count checks with seeded accounts. Add a synthetic hospital fixture with two tenants, two branches in one tenant, and receptionist, clinician, cashier and manager personas.
- [ ] Agree on the tenant/branch/assignment contract, the field visibility matrix, clinical/private storage, patient read audit and consent record semantics. The PRD proposes tenant-wide clinical records for treating staff with audited cross-branch access and a branch-only tenant option. Confirm this policy before building charts.
- [ ] Ask privacy, clinical and finance owners to approve the real-data launch gates. Record who owns privacy notices, guardian proof, retention, incident response, GST item classification and ABDM participation. Use synthetic data through engineering validation. Validate applicable dates and obligations against the official [DPDP Rules](https://www.meity.gov.in/documents/act-and-policies/digital-personal-data-protection-rules-2025-gDOxUjMtQWa) and [ABDM guidance](https://abdm.gov.in/strapicms/uploads/HIP_HIU_Guidelines_f85df336ec.pdf).

**Exit gate** · A signed-off access matrix, private storage design, isolation test matrix and pilot decision record. Any unanswered launch requirement stays visible with an owner and due decision.

## Phase 1 · Outpatient MVP

The PRD's week ranges are estimates. Re-estimate after Phase 0 and the first foundation PR pair, when team size and pilot requirements are known.

Phase 1 includes the PRD's core tenant, subscription, audit, notification, patient index, appointment, queue, patient billing, reporting, consent, dental and eye scope. Ship the minimum clinical templates and consent flows with their owning workflows. Keep the full tenant-configurable form/template editor in Phase 2. Confirm how much public booking and messaging must ship with the clinic release. The Phase 1 offline-tolerance item is a `Should` in the FRD. If included, scope it to approved reception actions, provisional tokens and explicit conflict review.

**MVP release gate** · Demonstrate one complete dental and one eye workflow using synthetic data, pass the role and isolation matrix, rehearse imports and restores, and get clinical, privacy and finance approval for the pilot. Adopt the PRD targets of registration-to-consultation under five minutes and onboarding under one day as measurements to validate with pilot operators. Size the PRD's uptime, latency, recovery and accessibility targets before promising an SLA. Run Chrome and Edge desktop/mobile and Safari smoke tests before real-data pilot use.

## Phase 2 · Revenue, operations and patient self-service

- [ ] Deliver insurance/TPA pre-authorization and claims, pharmacy and batch-stock dispensing, purchase and inter-branch transfers, optical orders and fitting, and dental lab work orders. Each workflow shares patient, order and financial references from Phase 1. Reconcile stock, dispensing, patient/insurer balances and returns before enabling each module.
- [ ] Add dental imaging and eye diagnostics with a private viewer. Start with managed uploads and metadata, then add device adapters when pilot needs are known. Add surgery/OT booking, higher-risk workflow checklists and follow-up, with required clinician review before release.
- [ ] Release the patient/guardian portal with verified OTP sign-in, dependent switching, scheduling, queue position, approved record downloads, payments and privacy requests. Start with responsive web. Decide the native app scope, notification provisioning and localization using pilot evidence.
- [ ] Implement physiotherapy modules 31–33 using the shared care plan and package balance. Deliver assessment and session notes first, then exercise programmes, equipment/modalities tracking and approved patient sharing. Verify one attended visit consumes a package unit once.
- [ ] Add facility/professional registry configuration, ABHA linking and ABDM M1/M2 behind flags after consent and the versioned clinical model are stable. The PRD calls for ABDM readiness at launch and schedules integration work in Phase 2. Treat readiness as a Phase 0 design decision and move the required certification work into the Phase 1 critical path if the pilot contract requires it. [National Health Authority guidance](https://abdm.gov.in/strapicms/uploads/HIP_HIU_Guidelines_f85df336ec.pdf)
- [ ] Expand tenant-facing configuration, onboarding/import tooling, support approvals, data export and platform usage views. Add the advanced chain dashboards after branch-level numbers reconcile.

**Exit gate** · A manager reconciles branch stock and claims, a guardian sees only linked dependents, an approved clinical document opens through the private access path, and provider-specific sandbox checks pass for every enabled integration.

## Phase 3 · Growth, quality and cross-provider exchange

- [ ] Add consent-aware recalls and follow-ups, feedback/NPS, approved external teleconsultation and quality/accreditation registers. Apply channel rules to every segment, including minors. Build campaign reporting from permitted event data.
- [ ] Add ABDM M3 read-only external records once M2 is accepted and consent revocation/expiry and source provenance are proven. Localize patient and staff experiences in Hindi/Gujarati based on pilot requirements.
- [ ] Verify opt-out, revocation and limited external access, reconcile new metrics against source records, and document recovery and support handoffs. Keep IVF behind its separate discovery and PRD gate. Full inpatient wards, in-house video and AI diagnosis remain outside the defined v1 scope.

## Immediate PR sequence

1. **Backend PR A** · Add branch/department/chair-room data and APIs, branch assignments and two-tenant isolation tests. Begin private clinical attachment policy work alongside the branch PR. The backend plan owns the exact split.
2. **Frontend PR A** · Add branch administration, branch selection, branch-scoped cache keys and permission states against the agreed contract. Start with fixtures while the API is built. Release only after the API and role tests pass.
3. **Paired PR B** · Add the patient index, duplicate review, guardian links and consent capture with read audit and private file handling. Keep real records gated until storage and authorization verification passes.
4. **Paired PR C** · Add the first registration → booking or walk-in → queue flow. Then add a signed dental encounter, the eye encounter and patient billing as independently testable slices.

For each slice, link frontend and backend PRs and list the DTO/API change, migration or flag, affected roles, and one browser scenario. Use `npm run check`, `npm run lint:hrefs` and `npm run build` in the frontend. Record any checkout-specific formatting adjustment. Add focused tests for new state transitions and permission decisions. Start with isolated environments, roll schema changes forward before enabling UI flags, and use pilot feedback before expanding rollout.
